## 7. 打造你的产研小队：让"每次都差不多"的脑力活自动化
前面六章，你做的大多是"信息整理"类的技能——早报、纪要、周报、竞品监控。这些是最容易交出去的活儿，因为输入输出都很清晰。
但你工作里真正吃时间的，往往不是这些。
如果你做过产品或者参与过研发流程，你一定经历过这种感觉：**每次发版都要写一遍 changelog，每次联调都要记一遍对接文档，每次需求评审都要把 PRD 从头捋一遍——内容每次都不一样，但流程每次都差不多。** 这种"半脑力活"最烦人：说它简单吧，确实要动脑子；说它难吧，又不值得你花两小时。
这一章，我们把这类活儿找出来，交给数字员工。
---

### 7.1 产研流程里，哪些环节适合交出去？

### 7.2 实操：从一个最痛的环节开始
别贪多。从上面那张表里，挑一个**你上周确实花了时间、而且下周还会再来一遍**的环节。
我们用"发布记录自动生成"举个例子——因为这个场景结构清晰、容易验证、而且几乎每个产研团队都有。
#### 😩 Before：
每次发版，你要翻 Git 提交记录、看 JIRA/飞书的需求单、找产品确认改了哪些功能、写一份对内的技术 changelog 和一份对外的版本说明。前后要花 30~60 分钟，而且总会漏掉某个改动。
#### 😎 After：
发版后，你把这周的提交记录或需求单列表丢给数字员工。它自动按模块分类，生成两份文档：一份给研发团队看的技术 changelog（包含具体改动和影响范围），一份给用户看的版本说明（只说功能变化，不提内部细节）。你审一遍就能发出去。
#### T1~T4 草稿：
- **T1 对象**：本次发版的提交记录 / 需求单列表
- **T2 动作**：按模块分类 → 区分对内/对外 → 分别生成技术 changelog 和用户版本说明
- **T3 格式**：两份独立文档，技术版包含（模块、改动项、影响范围），用户版包含（新功能、优化、修复）
- **T4 触发**：手动触发（每次发版后）
> 💡 这个场景跟第 4 章的套路一模一样：白纸列 T1~T4 → 用人话交给 Cursor → 检查三件事 → Accept → 验收。唯一的区别是，**输入物从"新闻""录音"变成了"提交记录""需求单"**——方法论完全通用。

### 7.3 设计协作接口：让产研小队真正跑起来
当你做了两三个产研类技能之后，自然会想：**能不能让它们串起来？**
比如这条链路：
> 用户反馈 → Bug 分类员整理 → 需求文档员补充进 PRD → 发布记录员在上线后自动更新 changelog
这就是模块三里学的"接力赛"模式，只是场景换成了产研。核心设计原则只有两条：
**① 每个技能的输出，必须是下一个技能能读懂的输入**
这听起来像废话，但很多人会踩坑。比如 Bug 分类员输出了一张漂亮的表格，但需求文档员需要的是"每个 bug 对应的功能模块和用户影响"。格式对不上，接力就断了。
**解决方法**：在每个技能的"输出格式"里，明确写出**下游需要的字段**。就像给实习生交代："你整理完之后，表格里必须有'功能模块'和'用户影响'这两列，因为下一个同事要用。"
**② 验收标准要写进技能文件，不要留在你脑子里**
"差不多就行"是协作的大敌。你觉得"差不多"，数字员工可能觉得"已经很好了"。
**解决方法**：在技能文件的执行步骤末尾，加一段"自检清单"：
```markdown
## 自检（输出前必须确认）
- [ ] 每个改动项都标注了影响的模块
- [ ] 对外版本说明里没有出现内部术语
- [ ] 修复类条目都附上了原始 bug 编号

```

数字员工会在输出前自己过一遍这张清单。不完美，但能挡住 80% 的低级错误。

### 7.4 沉淀：让每一次迭代都留下东西
产研流程最大的浪费，不是"这次写了一份文档"，而是**"下次又从零写了一份差不多的文档"**。
当你的产研技能跑了两三轮之后，建议做一件事：**回到 Cursor 里，把这几轮的实际输出跟技能文件对比一下**——哪些步骤每次都要手动补？哪些格式每次都要改？
把这些"每次都要改的地方"固化回技能文件。这就是卷首语里说的"让每一次迭代都留下可复用的技能与模板"。
> 📌 技能文件不是写完就不动了。它更像一份活的 SOP——每跑一轮，就精确一点。三五轮之后，你会发现新来的实习生（包括真人实习生）都可以照着这份技能文件来交付了。
